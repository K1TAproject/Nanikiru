# 画面辅助与统一观察数据：阶段设计

日期：2026-11-10。本文保留已讨论的五结构方案。同日后续用户已授权底层适配：五种记录和接口契约已落地，旧 UI/模拟器运行链已移除；最新范围见 [适配记录](direction-adaptation.md)、[分析接口](analysis-interface.md)。处理器与训练建议继续作为待讨论项，不因数据容器已建立而视为功能完成。

## 1. 当前目标与已确认原则

后续更新（2026-11-11）：五结构不变，已增加有限人工事件处理及专用新格式保存加载/回放；具体范围以[人工推进说明](manual-progression.md)为准。下文未落地的复杂事件与历史修订设计不代表已实现。

最终交互目标是“获取画面 → 识别并维护对局 → 分析 → 给出何切建议”。交互设备可包括手机摄像头、智能眼镜；具体首个设备、静态拍照或连续视频闭环尚未决定。不再把完成桌面模型评分闭环作为视觉方向的必经前置；同日后续清理已停用旧 UI 并移除强耦合模拟器，未来如需仿真工具另行适配。

| 模块 | 职责 |
| --- | --- |
| 交互 | 采集、传输、展示或播报结果、接受人工纠错 |
| 识别 | 输出单帧或片段的结构化观察与不确定性，不把遮挡当作牌消失 |
| 基础 | 定义数据、关联连续观察、确认动作、维护局面与历史、检查矛盾 |
| 分析 | 基于当时可见信息评价候选，支持固定计算与神经网络等多种实现 |

已确认的初步数据方向：

- 使用统一牌表；牌码直接包含赤牌身份（如 `0p`），不再重复存 `red`。
- 保留动作时序、玩家非牌属性与场况；不把所有信息塞入单张牌。
- 资格和分析结果尽量从事实推导，不独立维护门清、自风、立直、一发、振听等重复状态；有实测性能需要才引入可重建缓存。
- 鸣牌组、弃牌历史仍需表达，但不强制分别建立 `Meld`、`DiscardRecord` 等类。
- 未见牌统一作为未见库存，不猜测其真实去向；未见枚数不等于活牌山可摸枚数。
- 当前状态与历史、视觉证据与已确认事实、模型推测与事实分开。分析不得读取真实牌山、种子、对手暗手或未来公开信息。
- 标准记录格式与神经网络张量编码分开；使用同一事实输入不要求各算法具有相同的内部编码。

## 2. 五种基础结构

以下为讨论形成的主体方案，现已在 `models.py` 落地，并增加集合 `completeness`。Python 使用 `UNKNOWN` 与 `None` 区分未知和不存在；`observation-v1` 标识新容器结构，但没有文件加载/迁移器。具体落地差异以 [分析接口](analysis-interface.md) 为准。

### TileRecord：可引用的牌记录

| 字段 | 含义 |
| --- | --- |
| id | 本局记录编号，不承诺摄像头能跨遮挡识别物理实体 |
| code | `1m`～`9m`、`1p`～`9p`、`1s`～`9s`、`1z`～`7z`，赤五为 `0m/0p/0s`；可未知 |
| zone | 暗手、牌河、鸣牌、宝牌指示牌、里宝指示牌等当前区域 |
| seat | 当前区域关联的玩家；不是历史弃牌者，指示牌等不适用 |
| group_id | 所属已成立鸣牌组；其余不适用 |

花色、数值和赤牌身份从 code 解析；牌形计算归一化赤五，计分保留原始身份。公开时点、弃牌方式与历史来源查事件。未知暗手通常只记数量，不强制创建 136 条记录。已知牌移入鸣牌区只改变位置，不增加第二份库存。

### PlayerInfo：玩家基础信息

| 字段 | 含义 |
| --- | --- |
| seat | 固定座位 0～3 |
| score | 当前点数，可未知 |
| untracked_hand_count | 未逐张建档的暗手数量，可未知 |

暗手总数＝该玩家暗手区域记录数＋未建档数量；未知牌已有独立记录时也算在前者，不重复计数。摸入牌仍属于暗手，不能额外重复加一。新亮出的未建档暗手建立记录时同步扣减数量。玩家资格统一查询，不在此复制保存。

### RoundSnapshot：某个时点的局面

| 字段 | 含义 |
| --- | --- |
| round_id / rule_id | 本局标识、明确规则版本 |
| observer_seat | 观察者座位 |
| round_wind / hand_number / dealer_seat | 场风、局号、庄家 |
| honba / riichi_sticks | 本场与供托 |
| players / tiles | 四家信息、统一牌表 |
| groups | 组编号到鸣牌共同属性的关系表 |
| phase / actor | 行动阶段、主动行动者；共同响应另见 pending |
| draw_context | 当前摸牌者、牌引用、普通/岭上/未知来源；无摸牌时不适用 |
| pending | 当前响应对象、弃牌/抢杠窗口、已知响应 |
| remaining_draws | 剩余普通摸牌数；未知不能填零 |
| initial_context | 中途接入前已知但不能从现有历史恢复的事实与明确未知项 |
| completeness | 集合覆盖事实，区分已知空集合与未完整观察；不属于资格缓存 |

groups 每组保存 `kind`（吃/碰/大明杠/暗杠/加杠）、`called_tile_id`、`source_seat`；成员及持有者从牌表筛选。它保留必要的组关系，但无需独立鸣牌类。加杠通过事件保留原碰与追加过程，不能只覆盖最终类型而丢历史。

pending 中“尚未响应”“已过”“响应内容未知”不同。对手私有响应不得进入玩家观察。阶段须能表达待摸牌、待弃牌、待弃牌响应、待抢杠响应、待补牌、结束；无法判断阶段时应表达未知，不强制视为待弃牌。

initial_context 用于接入前的已成立立直、已知或未知振听/一发、开局中断情况、已有有序弃牌历史等。弃牌历史包含被鸣走的牌；只知道各家内部顺序时，不虚构跨玩家全局顺序。完整开局记录不重复填写可从事件推导的资格。

### Event：已确认的动作或状态变化

| 字段 | 含义 |
| --- | --- |
| id | 本局唯一且有序的事件编号 |
| kind | 事件种类 |
| actor | 行为玩家；系统确认可以不适用 |
| target_id | 响应或引用的事件 |
| data | 按事件类型限定并校验的必要参数 |

| 事件 | 必要内容 |
| --- | --- |
| 摸牌 | 牌引用或新牌信息、普通/岭上来源 |
| 弃牌 | 牌引用、手切/摸切/未知、是否宣言立直（独立字段） |
| 已提交响应 | 对象、过/吃/碰/杠/荣和、使用的牌 |
| 响应结束 | 已确认裁决结果或可观察的最终结果 |
| 鸣牌成立 | 组、类型、成员、来源弃牌 |
| 杠宣言 | 暗杠/加杠、牌、原碰组；与成立区分 |
| 立直成立 | 对应宣言；供托扣除按规则处理 |
| 指示牌生效 | 牌、顺序和生效时点 |
| 和牌/流局成立 | 原因、和家/来源、已确认听牌等信息 |
| 结算 | 役番符/支付明细、点数变化、下一局场况 |

非法请求不成为已执行事件；实际提交但尚未裁决的意向可作为响应事件。不能同时将“提交意向”和“成立”各应用一遍库存变化。结算原始参数与派生明细的权威关系须在落地前确定，保证扣棒和支付各执行一次。

事件顺序用于规则，巡目用于派生展示；摄像头时间戳属于证据，不替代动作编号。外部画面只确认“窗口结束且无人鸣牌”时，不补造各家的私有响应或合法和牌机会。

### RoundRecord：记录容器

| 字段 | 含义 |
| --- | --- |
| schema_version | 格式版本 |
| initial_snapshot | 开局或接入时快照 |
| events | 此后的已确认有序事件 |
| coverage | 从开局/中途开始、已知漏失区间等覆盖信息 |

权威记录为初始快照＋后续事件；当前快照可重建，运行时可维护但不能独立改写造成双源。存在不能重建的缺口时，不宣称能连续回放整个真实牌局。

## 3. 规则所需信息与推导边界

| 判断 | 所需事实 |
| --- | --- |
| 手牌、牌河、鸣牌、库存 | 牌表、组关系、初始弃牌历史、后续事件；鸣走牌只计一次 |
| 门清、自风、向听/等待 | 已成立组、座位庄家、已知手牌；暗手拆分由算法计算，不预先锁定 |
| 吃碰杠、食替、立直后杠 | 手牌、来源事件、座位、阶段、规则、必要的此前等待 |
| 立直/双立直/一发 | 宣言与成立、首弃条件、动作顺序与中断；摸切与立直可同时成立 |
| 舍牌振听 | 当前全部等待与全部自家弃牌历史，含已鸣走牌 |
| 临时/立直后见逃振听 | 当时手牌、等待、响应结束事实、立直时点与解除事件；不能用“没看到和牌”代替过牌 |
| 四风连打 | 四家各自首弃为相同风牌、开局中断、最终响应；不是前四巡 |
| 四家立直/三家荣和 | 已成立立直、同一响应窗口及最终裁决 |
| 九种九牌/四杠散了 | 首摸手牌与中断、杠数量和持有者、第四杠后补牌/响应进度 |
| 荒牌/流局满贯 | 普通摸牌余量、最后响应、终局听牌、弃牌及被鸣历史、规则 |
| 和牌合法性/番符 | 完成牌形、组明暗、和牌张、场风自风、振听、役与时机；宝牌不是役 |
| 岭上/抢杠/海底河底/天和地和 | 摸牌来源、当前响应、最后普通摸牌、首次摸牌与中断 |
| 宝牌/里宝/包牌/支付 | 指示牌生效与揭示、鸣牌来源、和家放铳者、庄闲、本场供托及规则 |
| 换庄/连庄/场风/整场结束 | 结束原因、听牌与和家、局进度、点数、赛制；流局不必然换庄或换场风 |

查询结果区分成立、不成立、无法确定；存在矛盾时不能冒充普通未知或正常局面。规则版本固定细节，本文不宣称已覆盖所有日麻规则变体。

## 5. 待讨论：中途接入与输入冲突

本节是风险分析和处理建议，尚未决定具体编码、流程及实现范围。

### 中途接入

完整历史不总能恢复：当前牌面不能确定此前一发是否中断、见逃振听、各家跨玩家动作顺序、已有碰是否曾加杠。initial_context 与 coverage 可以承载缺失，不能创造缺失事实。

建议按能力降级：自家手牌完整时可计算牌形；公开牌覆盖不足时不能把未见枚数说成精确值；响应/振听未知时不确认荣和合法性；对手终局暗手/听牌未公开时不自行完成确定支付。明确区分“可以表示这个局面”和“信息足够执行某种分析”。

建议首个接入验收使用稳定的自家待弃牌局面，允许中途开始；是否支持摸打/鸣牌动画中的任意时点接入待确认。这是新建议，不扩大旧 Recorder 的已实现范围。

需补齐的字段语义：

- `null` 的未知/不适用区分、缺失与矛盾状态如何编码。
- `initial_context` 的明确子结构，包含缺失弃牌、未知来源、首巡与私有资格，不作为任意扩展袋。
- 暂存未决杠、延迟翻宝、岭上容量、指示牌顺序如何在任意中途快照中无歧义表达。
- 同牌实体无法追踪时的引用关联；不得凭视觉猜测区分相同普通牌的历史身份。

### 前后信息不一致

建议流程：原始观察 → 候选解释 → 一致性校验 → 提交已确认事件。观察证据属于识别层，五种规则结构不是完整的视觉证据格式。

| 情形 | 建议处理 |
| --- | --- |
| 重复帧、遮挡 | 不重复记动作，不因暂时看不到而删牌 |
| 同一牌 3p/5p 识别冲突 | 保留候选与证据，核实或人工纠正；不直接覆盖可信历史 |
| 库存超限、张数不符、赤牌矛盾 | 拒绝提交矛盾解释，保留最后一致状态 |
| 漏掉若干动作但后续局面可确认 | 标记缺口；必要时建立新的接入片段，不伪造唯一动作链 |
| 回头纠正旧识别 | 保留原证据和修订关系，重建受影响局面，废弃旧建议与样本缓存 |
| 无法确定当前局面 | 标记建议过期或受限，不继续把最后可信状态当成实时状态 |

候选/证据 ID、源时间、修订号、质量标记及建议关联版本属于待定的采集与修订协议，不在本轮冒充新增已确认核心字段。历史修正后要区分“当时在线系统知道的内容”和“事后校正内容”，两者不能混为一类训练样本。

## 6. 待讨论：算法、模型与训练数据

已确认希望支持固定计算与神经网络等多种推荐实现；下述编码、训练目标与顺序属于建议。

### 共用语义，不强制共用张量

建议输入为：决策时点可见快照＋截至该时点的可见历史＋覆盖/未知信息＋候选动作及合法性依据。候选不能借助对手暗手、未来牌或私有响应过滤；外部观察不完整时，明确区分合法、非法、待确认，而非把未知全部填入二元合法掩码。

固定算法可直接使用结构与派生特征；神经网络增加独立编码器。编码建议包含自家牌计数及赤牌信息、分玩家有序弃牌、鸣牌/来源、场况点数、已知数量、派生资格及其未知掩码、必要历史。记录 ID 不作为有序数值特征；座位相对观察者归一化。同码手切/摸切是否合并为训练标签需按任务明确，不能丢失执行动作身份。

训练样本建议关联局/整场 ID、记录修订与格式版本、决策时点、观察者、来源、规则、特征版本、行动前输入、候选、实际动作和标签来源。终局收益可以是训练目标，不可进入行动前特征。策略概率、启发式分数、期望点数不能混为相同的“正确率”。

### 数据来源与适用目标

| 来源 | 可行用途 | 边界 |
| --- | --- | --- |
| 未来适配的模拟器与基础策略 | 调试导出、生成合法序列、基准标签/蒸馏、后续自对弈实验 | 旧 Game 已移除，需另行选用/适配环境；基础策略不是高手标签 |
| 自己导出的完整牌谱 | 小规模导入验证、行为模仿、结果标签 | 必须按玩家时点过滤全知信息；实际动作不等于最优动作 |
| 外部牌谱/研究数据 | 扩大行为样本、离线训练与评测 | 来源许可、完整性、规则差异、格式与下载可用性需单独核实 |
| 人工校验题目 | 边界验收、专家对比 | 量少，不能独自覆盖真实局面分布 |
| 摄像头图像/视频 | 识别、时序跟踪及缺失鲁棒性训练 | 需要框/牌码/区域/动作等标注；结构化牌谱不自动提供真实图像标签 |

本轮查到的技术参考（2026-11-10，只阅读说明，未下载数据、安装或集成）：

- [Mortal](https://github.com/Equim-chan/Mortal)：已有日麻深度强化学习开源实现，可供输入/训练方式研究，不代表本项目已兼容其模型。
- [mjlog2mjai](https://github.com/fstqwq/mjlog2mjai)：已有天凤 MJLOG XML 到 MJAI JSON 的转换工具，说明牌谱事件转换有可参考路径；不能假设工具输出可直接套用本项目规则。
- [tenhou-to-mjai 说明](https://github.com/NikkeTryHard/tenhou-to-mjai/blob/main/README.md)：检索到其工具及预处理数据说明；本轮未验证数据文件可下载性、质量或使用许可，不将其算作已获取训练集。

建议先做行为模仿或固定算法蒸馏以验证流程；若目标是超越固定基准，再讨论强策略标签、离线强化学习或自对弈。具体训练目标、框架和硬件预算未定，不承诺强度与训练耗时。

训练/验证/测试至少按完整对局分组；存在整场记录时按整场分组，并先去重再划分。同一局不同玩家视角、修订版本不能跨集合。完整牌谱训练还需评估中途接入/漏拍场景的分布差异，缺失模拟应保留真实未知边界。
