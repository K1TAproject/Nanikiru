## 用户已确认的目标与方向

- 项目的主要目的是练习模型训练、数据处理以及接口调用与封装。界面服务于实验，但用户已明确要求清晰简洁的图形牌桌，不能仅用文字输出局面。
- 产品定位调整为桌面四人日麻何切训练软件：随机开始牌局，玩家与三家训练好的机器人对局，出牌后显示该切评分，保存逐切记录并汇总整局训练评分。产品边界与后续步骤见 `training-product.md`。
- 优先评估切牌质量；对吃、碰、杠、立直等动作的训练评价后续扩展。游戏规则仍须支持这些动作，才能承载完整对局。
- 最终分析综合牌效、打点和防守，并根据公开信息评估各家的推进与威胁。
- 摄像头监控与何切推荐作为共享评估系统的后续应用：先适配雀魂画面，再适配手机摄像头回传的实体牌桌画面；智能眼镜接入是远期方向。
- 用户已接受 Python 为主、不依赖图形界面的第一阶段记录库方向，第一阶段目标见 `phase-1.md`。
- 用户随后要求简单可视化调试工具：使用独立 Tkinter 窗口展示数据、提交操作和显示测试输出。核心库仍不依赖界面。特殊动作以构造器注册接口预留，当前不实现其规则。
- 2026-09-15 新确认：增加完整游戏状态和真实牌山，可复现洗牌发牌，自动摸牌、手动弃牌；切换四位玩家视角，另设明确标记的全知调试视角。以游戏环境和玩家观察接口为下一步基础，之后再接牌谱、模型与视觉。

## 当前目标的架构方向

2026-09-17：增加独立役种决策模块与条件吃碰投影，和基础牌效分开记录；新/旧机器人可切换。保守启发式、v4 兼容及固定对比案例见 `yaku-decisions.md`。

本轮交付：随机开局、响应处理、吃碰杠、立直、和牌、流局及单局自动结算；默认庄家人工、三家基础牌效机器人，保留全人工调试。默认四人东，场风可选东南西北；三家依次响应后统一裁决。非法操作保留最后合法局面与已有合法响应，显示原因并暂停；修正或撤销后显式恢复，不强行放行、不自动扣分。关闭赤宝保留赤五身份，仅取消赤宝加番。新杠宝可关闭，杠与补牌仍执行。基准规则与测试见 `rules-and-settlement.md`。

```text
游戏环境（四家真实手牌、真实牌山、公共状态）
          ↓ 玩家观察接口              ↓ 独立全知调试入口
指定玩家可见信息 → 图形牌桌/未来机器人   全知调试视图
          ↓ 提交弃牌等决策
环境校验 → 收集所需响应 → 统一裁决 → 摸牌/结算 → 更新观察与事件
```

环境负责牌的来源和规则推进，调用者不能指定下一张实际摸入的牌。全知状态与玩家观察分开；未来牌谱转换与视觉输入也应适配相同含义的玩家观察。完整界面不是模型核心，核心仍须无界面运行。具体范围、UI要求、步骤和验收见 `game-environment.md`。

## 已有记录工具的架构方向（保留参考）

先做单个 Python 项目，模块通过普通函数或对象调用协作，不提前拆成网络服务。

```text
手动提交 / 牌谱导入 / 视觉识别
              ↓
       输入转换与动作确认
              ↓
    牌局核心：状态、动作、校验
          ↓             ↓
      历史与保存      分析与模型推理
          ↓             ↓
      训练与评测      建议与辅助展示
```

- 第一阶段只做手动入口、核心记录、保存与回放。
- 首套代码使用 Python 3.11+、`dataclass`、枚举和 JSON；运行与测试无第三方依赖。本机验证版本为 3.11.4。
- 不采用此前讨论过的 Tauri/Vue/Rust 桌面优先方案。
- 手机或其他程序需要外部访问时，再包装网络接口。
- 基础牌效算法先作为确定性基准；模型训练用于后续比较和改进，不是记录库的依赖。
- 先完成训练软件的游戏、机器人和评分闭环，再进行视觉识别与摄像头输入开发。

## 已有记录库的首次交付约定（不替代新环境目标）

- 首套代码实现普通摸打、校验、保存、加载、回放和撤销，通过 Python 示例脚本调用。
- 必须支持中途接入，首版接入点限定为自家已摸牌、尚未弃牌的稳定局面。
- 初始快照必须包含场况、庄家、观察者、点数、自家完整暗手及单独标记的摸入牌、各家有序牌河与副露、立直状态及公开宝牌指示牌。对手暗手以未知数量表示。
- 可含已存在的副露与立直；记录开始后的新鸣牌或立直事件暂不支持，明确报错并保持记录不变。
- 接入前的全局动作顺序、摸切等未提供的信息保持未知，不虚构历史；回放从初始快照开始。
- 下一次合法摸牌自动表示上一弃牌无人响应，不推断各家是否放弃了合法和牌机会。
- 自动校验以记录一致性为边界；听牌、和牌、振听等特殊判定后续加入。
- 规则方向固定为四人东风战、有赤五、有新杠宝；各种流局暂不处理，也不自动结算或管理整场晋级。
- 可摸牌山耗尽后结束本次摸打流程；最后一张摸牌仍允许正常弃牌，再关闭流程，不在刚摸入最后一张时跳过弃牌。
- 测试人员可随时停止记录。实现上将其作为可保存、恢复的记录暂停，不冒充麻将和牌或流局结果。
- 支持撤销最近动作；修正更早动作时回退到错误之前，再重录后续动作。

### 剩余可摸牌数

用户要求中途接入时自动计算，不要求测试人员另填剩余牌数。计算必须使用暗手张数（含未知张数和摸入牌）、副露实际张数及未被鸣走的弃牌，不能只数牌河。

实现方案：在完整、稳定且补牌已完成的四人快照中，以总牌数 136、保留牌数 14 为基础，剩余可摸数为 `136 - 14 - 各家暗手总张数 - 副露实际总张数 - 未被鸣走的弃牌总张数`。杠按四张计，摸入牌只计一次，宝牌指示牌属于保留牌，不额外扣除。初始副露的被鸣牌必须有一致的去向记录，避免重复计数。

该公式已通过无副露、吃碰、三类已完成杠补牌快照和最后一摸案例验证。不得用于未完成杠补牌等中间状态；不完整或矛盾快照应报错，不能猜出精确剩余数。首版新杠事件尚不支持。

## 数据建模原则（实现约束）

1. 当前状态表示“现在是什么”，动作历史表示“如何变成现在”。
2. 所有更新通过统一动作入口：校验、更新、记录应一起成功或一起失败。
3. 初始状态加顺序动作应能确定地还原当前状态。
4. 一名玩家可见的信息与对手未知暗手分开表达；训练用全知信息不得泄漏到决策输入。
5. 牌局事实、视觉证据和模型推测分开保存。可推导数据优先计算，避免多份可修改事实。
6. 原始素材、标准化记录、训练样本分开；未来可重建样本，不必重复采集。

## 数据模型与首版落地差异

以下保留旧记录库的设计结构；实际接口以 `nanikiru/models.py` 和 README 为准。新 Game 另用 `Decision` 表达响应、立直和杠等动作；`GameState.pending` 保存待裁决响应及宣言，`Phase.ENDED` 表示已结算。旧 Recorder 仍只接受 `Draw`/`Discard`。

### Tile：已知牌

- `suit`：万、筒、索、字。
- `rank`：数牌 1～9，字牌编码需明确约定。
- `is_red`：赤牌标记。
- 暂不需要为 136 张实体牌分配编号；相同普通牌以重复元素表示。
- 未知牌不伪装成某个特殊花色。

### HandState：暗手牌信息

- `known_tiles`：已知暗手牌，不含单独记录的摸入牌。
- `unknown_count`：未知暗手牌数量，不含单独记录的摸入牌。
- `drawn_tile`：区分“无摸入牌”“摸入未知牌”“摸入已知牌”，具体类型待定。
- 手牌总数由这些信息推导。
- 手切后应把摸入牌并回暗手；摸切则移除摸入牌。

### Discard：有序弃牌

- `tile`：弃牌，包含赤牌信息。
- 弃牌具有记录内唯一引用标识；初始快照弃牌不要求有历史事件编号，接入后弃牌可关联事件。
- `is_tsumogiri`：摸切、手切、未知三种情况。
- `is_riichi_declaration`：是否为立直宣言牌。
- `claimed_by`：被鸣走时的玩家，否则为空。
- 被鸣走的牌保留历史，但不能与副露重复计入可见牌数量。

### Meld：副露与杠

- `kind`：吃、碰、明杠、暗杠、加杠。
- `tiles`：组成牌及赤牌信息。
- `source_discard_id`：来源弃牌的引用标识；可指向初始快照牌河，不强制指向接入后事件；暗杠为空。
- 加杠保留原碰的来源，历史中分别记录碰与加杠。

### PlayerState：玩家状态

- `seat`：固定座位编号 0～3，编号方向待约定。
- `score`、`hand`、`discards`、`melds`。
- `riichi_status`：未立直、宣言待成立、已成立。
- 自风从固定座位和庄家推导，不把“东家”当作永久身份。

### RoundState：单局状态

- 场风、局数、本场、供托、庄家、观察者座位。
- 四位玩家状态、公开宝牌指示牌。
- 行动阶段及相关玩家或事件。
- 结束结果：未结束时为空。
- 阶段建议区分等待摸牌、等待弃牌、等待弃牌响应、等待抢杠响应、等待补牌、已结束。
- 弃牌不应无条件立即切换到下家摸牌，需要处理响应窗口。
- “宝牌指示牌”与开杠后的“岭上补牌”是不同概念。

### Action / Event / RoundRecord

- 动作按类型表达，各自包含必要参数，避免大量可空字段的通用大字典。
- 首批动作是摸牌、弃牌；之后加入鸣牌、立直和结束事件。
- 成功提交后生成带顺序编号的事件。
- 建议保存 `schema_version`、`initial_state`、`events`，回放恢复当前状态。
- 初始状态不能与运行状态共享可被后续修改的对象。
- 时间戳不是首期规则运行的必要条件；视觉接入时再关联视频位置与识别证据。

## 未冻结的实现建议与后续问题

- 赤牌具体数量尚未由用户单独明确；暂建议万筒索各一张，不表述为用户已确认数量。
- 保存暂建议显式调用，不自动保存；用户确认撤销方案，但未单独确认自动保存策略。
- 固定座位沿摸打顺序编号、字牌编码和具体 Python 类型由实现时说明，属于技术约定。
- 从四家 13 张开始的开局初始化是旧建议，不是首版必要入口；不得因此阻止中途接入。
- 新增立直、杠和翻宝时序、多家和牌、流局、结算和整场结束留到对应后续任务再明确。

## 后续训练约束

- 决策输入只能包含行动发生时玩家可获得的信息。
- 实际牌谱切牌是行为样本，不默认是最优标签。
- 训练前明确目标和评测基准；至少按完整对局划分训练与测试数据。
- 对手听牌概率、危险度与推荐结果属于分析，不覆盖原始牌局事实。
